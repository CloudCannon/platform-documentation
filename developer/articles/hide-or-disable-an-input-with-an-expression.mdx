The `hidden_if` and `disabled_if` input options take an expression. An expression lets you show, hide, or disable an input based on the values of other inputs in the same file, so the editing interface changes as a *Team Member* works.

For example, a page that holds either a video or an image needs only one of the two path fields at a time. An expression on each path input hides the field that does not apply.

CloudCannon evaluates your expression whenever a value it reads changes, and updates the editing interface immediately.

These instructions assume you know which input you want to control and where in the configuration cascade you want to configure it. For more information, please read our documentation on [what inputs are](/documentation/user-articles/what-are-inputs/) and [using the configuration cascade](/documentation/developer-articles/using-the-configuration-cascade/).

To control an input with an expression:

1. Open your website files in your local development environment, or log in to CloudCannon and select the *Site* for which you want to configure your input.
2. Navigate to the location in the configuration cascade where you want to configure your input.
3. Identify the `_inputs` key, or create one at that level of the configuration cascade.
4. Add an input name key for the input you want to control under the `_inputs` key.
5. Set the `hidden_if` or `disabled_if` key under your input name key to your expression.

CloudCannon will now apply your expression to all markup files that use your input name key, without needing to save your configuration. This allows you to change your expression and see the result in your inputs live.

When you are happy with your expression, you must save your configuration.

In the following example, `type` is `video`, so the `video_path` input is shown and the `image_path` input is hidden. `published` is `true`, so the `slug` input is read-only.

<comp.CodeBlock language="Markdown" source="post.md">
```

---
type: video
video_path: /uploads/launch.mp4
image_path:
published: true
slug: launch-week
---

Content goes here.

```
</comp.CodeBlock>

<comp.MultiCodeBlock language="YAML" translate_into={["json"]} source="cloudcannon.config.yml">
```

_inputs:
  type:
    type: select
    options:
      values:
        - video
        - image
  video_path:
    type: url
    hidden_if___1___: 'type != "video"'
  image_path:
    type: url
    hidden_if: 'type != "image"'
  slug:
    type: text
    disabled_if___2___: published

```
<comp.Annotation number="1">

The `video_path` input is hidden whenever `type` holds anything other than `video`.

</comp.Annotation>
<comp.Annotation number="2">

The `slug` input is visible at all times, but becomes read-only once `published` is truthy.

</comp.Annotation>
</comp.MultiCodeBlock>

In YAML, quote your expression if it starts with a character YAML reserves, such as `!` or `*`, or if it contains a colon. Quoting is always safe, so quote every expression if you are unsure.

<comp.Notice info_type="info">
  The `hidden` and `disabled` keys take a boolean. `hidden: true` hides an input outright, and an input with none of these keys is visible and editable. If you set both `hidden` and `hidden_if`, the input is hidden when either is truthy, and the same applies to `disabled` and `disabled_if`.
</comp.Notice>

## Explain why an input is disabled

Set the `disabled_message` key to show a message while an input is read-only. CloudCannon shows the message with the input's comment whenever `disabled` is `true` or `disabled_if` is truthy, and hides it otherwise. The message supports the same limited Markdown as `comment`.

In the following example, `published` is `true`, so the `slug` input is read-only and shows the message.

<comp.CodeBlock language="Markdown" source="post.md">
```

---
published: true
slug: launch-week
---

Content goes here.

```
</comp.CodeBlock>

<comp.MultiCodeBlock language="YAML" translate_into={["json"]} source="cloudcannon.config.yml">
```

_inputs:
  slug:
    type: text
    disabled_if: published
    disabled_message: Unpublish this post to change its URL.

```
</comp.MultiCodeBlock>

## Reference the value of another input

A bare name in an expression refers to a sibling input, meaning an input in the same object as the input you are configuring. CloudCannon starts looking for every bare name in that object, which these instructions call the containing object.

Two reserved names let you reach the input you are configuring, or the top of the file.

<comp.OptionsTable>
  <comp.OptionsRow label="this" type_markdown="`any`">
    The input you are configuring. In a comparison, this is its value.
  </comp.OptionsRow>
  <comp.OptionsRow label="$" type_markdown="`any`">
    The top level of the file, or the nearest enclosing *Structure* value when the input sits inside a *Structure*.
  </comp.OptionsRow>
</comp.OptionsTable>

These names are only reserved at the start of a path. After a dot they are ordinary keys, so `hero.this` reads a key named `this` inside `hero`.

An expression reads the file a *Team Member* has open. It cannot read another file, another *Site*, or anything outside that file, so you cannot hide an input based on a value that lives elsewhere.

Read a nested value with a dot, such as `seo.title`, and an array item with its index, such as `authors[0]`.

Reading a key that does not exist gives you `null` rather than an error, so your expression keeps working while a *Team Member* fills in a file.

In the following example, the `caption` and `alt_text` inputs sit inside an `image` object in your content file, so a bare name would only reach their siblings inside that object. `show_captions` and `seo.locked` sit at the top level of the file, so each input reaches them through `$`. With these values, `caption` is hidden and `alt_text` is read-only.

<comp.CodeBlock language="Markdown" source="page.md">
```

---
show_captions: false
seo:
  locked: true
image:
  path: /uploads/hero.jpg
  caption:
  alt_text: A sunrise over the harbour
---

Content goes here.

```
</comp.CodeBlock>

<comp.MultiCodeBlock language="YAML" translate_into={["json"]} source="cloudcannon.config.yml">
```

_inputs:
  caption:
    type: text
    hidden_if: $.show_captions === false
  alt_text:
    type: text
    disabled_if: $.seo.locked

```
</comp.MultiCodeBlock>

### Climb to an enclosing object

Two functions move between inputs. Both take an input as their first argument rather than a value, so `parent(this)` is the object containing the input you are configuring, not the parent of its value.

<comp.OptionsTable>
  <comp.OptionsRow label="parent(input, levels)" type_markdown="`any`">
    The object or array `levels` above `input`. Both arguments are optional: `input` defaults to `this` and `levels` to 1, so `parent()` is the containing object, `parent(2)` is the one above that, and `parent($)` is the one containing the nearest *Structure* value.
  </comp.OptionsRow>
  <comp.OptionsRow label="get(input, ...keys)" type_markdown="`any`">
    Follows a path of keys or array indexes starting at `input`. `input` is optional and defaults to the containing object, so `get("seo", "title")` is the same as `seo.title`, and `get(parent(2), "currency")` reads from two levels up.
  </comp.OptionsRow>
</comp.OptionsTable>

### Inputs inside an array

An input inside an array item reads its siblings from that item, exactly as it would anywhere else. The item is its containing object, so `parent()` gives you the item, `parent(2)` gives you the array, and `parent(3)` gives you the object holding the array.

In the following example, each tier hides its own `annual_price_suffix` input until that tier has an annual price, so the suffix is shown for `Pro` and hidden for `Free`. The `name` input climbs three levels with `parent(3)` to read `currency` from the object that holds the array, and is read-only in both tiers because the currency is `NZD`.

<comp.CodeBlock language="Markdown" source="pricing.md">
```

---
currency: NZD
pricing_tiers:
  - name: Free
    annual_price:
    annual_price_suffix:
  - name: Pro
    annual_price: 120
    annual_price_suffix: per year
---

Content goes here.

```
</comp.CodeBlock>

<comp.MultiCodeBlock language="YAML" translate_into={["json"]} source="cloudcannon.config.yml">
```

_structures:
  pricing_tiers:
    values:
      - value:
          name:
          annual_price:
          annual_price_suffix:
        _inputs:
          annual_price_suffix:
            type: text
            hidden_if: '!annual_price'
          name:
            type: text
            disabled_if: 'parent(3).currency == "NZD"'

```
</comp.MultiCodeBlock>

#### Configuration on an array item

Configuration on the array item itself, such as `items[*]`, behaves differently. The containing object of an array item is the array, which has no keys, so a bare name there matches nothing. Use `this` to read the item's own values, for example `this.name` rather than `name`. `parent()` is the array and `parent(2)` is the object holding it, one level fewer than for an input inside the item.

<comp.Notice info_type="info">
  `$` stops at the nearest enclosing *Structure* value rather than continuing to the top level of the file. An input inside a *Structure* value cannot reach the file root with `$`, so climb with `parent($)` instead. Note that this makes the Structure less portable as it depends on data outside of itself.
</comp.Notice>

## Operators

You can use a subset of JavaScript operators in your expressions. If you know JavaScript, these behave as you expect, with the conversion rules below.

<comp.OptionsTable>
  <comp.OptionsRow label="! &amp;&amp; || ??" type_markdown="`Logical`">
    Negation, and, or, and nullish coalescing. `&&` and `||` return one of their two sides rather than a boolean.
  </comp.OptionsRow>
  <comp.OptionsRow label="== != === !==" type_markdown="`Equality`">
    `==` and `!=` treat a numeric string as a number when the other side is a number, so `2 == "2"` is `true`. `===` and `!==` do not, so `2 === "2"` is `false`. No other conversion happens, so `0 == false` is `false`.
  </comp.OptionsRow>
  <comp.OptionsRow label="&lt; &lt;= &gt; &gt;=" type_markdown="`Comparison`">
    Compare two numbers or two strings. A numeric string is compared as a number when the other side is a number, the same as `==`. Any other mix of types gives `false`.
  </comp.OptionsRow>
  <comp.OptionsRow label="+ - * / %" type_markdown="`Arithmetic`">
    Arithmetic on numbers. `+` joins its two sides into a string when either side is a string and the other is a string or a number, so `"a" + 1` is `"a1"`. Any other arithmetic on a value that is not a number gives `null`, so `"2" * 3` is `null`.
  </comp.OptionsRow>
</comp.OptionsTable>

Values follow JavaScript truthiness, so `null`, `false`, `0`, and an empty string are all falsy. You can write `null`, `true`, `false`, numbers, quoted strings, and array literals such as `[1, 2]` directly in an expression, and group with parentheses.

The ternary operator, bitwise operators, and the exponent operator `**` are not available. Neither are regular expressions, assignment, or more than one statement in a single expression.

## Functions

Nine functions work on values, alongside `parent` and `get` described above. A function that receives a value of the wrong type gives `null`, except for `includes`, `starts_with`, and `ends_with`, which give `false`.

<comp.OptionsTable>
  <comp.OptionsRow label="length(value)" type_markdown="`Number`">
    The number of characters in a string, items in an array, or keys in an object.
  </comp.OptionsRow>
  <comp.OptionsRow label="includes(haystack, needle)" type_markdown="`Boolean`">
    Whether a string contains a substring, or an array contains an item.
  </comp.OptionsRow>
  <comp.OptionsRow label="starts_with(value, search)" type_markdown="`Boolean`">
    Whether a string starts with another string.
  </comp.OptionsRow>
  <comp.OptionsRow label="ends_with(value, search)" type_markdown="`Boolean`">
    Whether a string ends with another string.
  </comp.OptionsRow>
  <comp.OptionsRow label="lowercase(value)" type_markdown="`String`">
    A string converted to lowercase.
  </comp.OptionsRow>
  <comp.OptionsRow label="uppercase(value)" type_markdown="`String`">
    A string converted to uppercase.
  </comp.OptionsRow>
  <comp.OptionsRow label="trim(value)" type_markdown="`String`">
    A string with leading and trailing whitespace removed.
  </comp.OptionsRow>
  <comp.OptionsRow label="number(value)" type_markdown="`Number`">
    A numeric string converted to a number. A number passes through unchanged.
  </comp.OptionsRow>
  <comp.OptionsRow label="string(value)" type_markdown="`String`">
    A number or boolean converted to a string. A string passes through unchanged.
  </comp.OptionsRow>
</comp.OptionsTable>

In the following example, the `summary` input stays hidden until `body` holds at least 200 characters, the `discount_code` input is read-only unless the code starts with `PROMO` in any capitalization, and the `permalink` input locks itself once it holds a value by reading `this`. `length` gives `null` for an empty input rather than zero, so `?? ""` keeps each comparison working before a *Team Member* has typed anything. With these values, `summary` is hidden, `discount_code` is editable, and `permalink` is read-only.

<comp.CodeBlock language="Markdown" source="product.md">
```

---
body: A short draft.
summary:
code: promo-spring
discount_code:
permalink: /products/spring-jacket
---

Content goes here.

```
</comp.CodeBlock>

<comp.MultiCodeBlock language="YAML" translate_into={["json"]} source="cloudcannon.config.yml">
```

_inputs:
  summary:
    type: textarea
    hidden_if: 'length(body ?? "") < 200'
  discount_code:
    type: text
    disabled_if: '!starts_with(uppercase(code), "PROMO")'
  permalink:
    type: url
    disabled_if: 'length(this ?? "") > 0'

```
</comp.MultiCodeBlock>

## Reference a key that is not a valid name

A bare name works only for key names that are valid identifiers: letters, digits, underscores, and dollar signs, not starting with a digit. In an expression, `draft-status` parses as `draft` minus `status`.

Reach any other key with `get`. On its own, `get("draft-status")` reads a sibling of the input you are configuring. Give it an input first to read from elsewhere, such as `get($, "draft-status")` for a key at the top level of the file. Square brackets with a quoted string work on any value too, so `$["draft-status"]` is the same as `get($, "draft-status")`.

A quoted key is always a key name, never a reserved name, so `get("this")` reads a sibling input literally named `this`.

In the following example, the `body` input reads `draft-status` from the top level of the file, and the `intro` input reads a sibling input with the same name. Both are hidden while `draft-status` is `incomplete`.

<comp.CodeBlock language="Markdown" source="post.md">
```

---
draft-status: incomplete
intro:
body:
---

Content goes here.

```
</comp.CodeBlock>

<comp.MultiCodeBlock language="YAML" translate_into={["json"]} source="cloudcannon.config.yml">
```

_inputs:
  body:
    type: markdown
    hidden: '$["draft-status"] === "incomplete"'
  intro:
    type: textarea
    hidden_if: 'get("draft-status") === "incomplete"'

```
</comp.MultiCodeBlock>

## Limits

An expression cannot change a value. It only controls whether an input is visible or editable.

An expression can be up to 1000 characters long and nest up to 32 levels deep. CloudCannon shows an error on the input itself when an expression exceeds either limit or cannot be parsed, so you can find and correct it.

While an expression is invalid, CloudCannon falls back to the safer option for each key. An input with an invalid `hidden_if` expression stays visible, so no content disappears, and an input with an invalid `disabled_if` expression stays read-only, so no value changes by accident.

An expression changes what a *Team Member* sees, but every key stays in your file. If you want the keys that do not apply to be removed instead, please read our documentation on [swapping an input's keys with a structure](/documentation/developer-articles/swap-an-inputs-keys-with-a-structure/).

For the full list of configuration keys available for inputs, please read our [Inputs](/documentation/developer-reference/configuration-file/types/_inputs/) reference documentation.
