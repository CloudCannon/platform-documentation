<comp.Notice info_type="important">
  Managing your SSL certificate on CloudCannon requires you to host your <comp.GlossaryTerm term="/user/glossary/s/site.yml">Site</comp.GlossaryTerm> through CloudCannon. If you are hosting your *Site* through an external service, please review their documentation on SSL certification.
</comp.Notice>

An SSL certificate (or a TLS certificate) is a periodically regenerated digital certificate that supports your website's authenticity and enables encryption for greater security between your web server and the visitor's browser. SSL certification is important to:

* Prevent others from intercepting the information passing between the server and the browser.
* Help users distinguish between the real version of your website and any fake versions created by other people.
* Verify ownership of a website.

CloudCannon recommends an SSL certificate for every website you edit on CloudCannon.

## HTTP vs HTTPS

<comp.GlossaryTerm term="/user/glossary/h/http.yml">HTTP</comp.GlossaryTerm>, or the HyperText Transfer Protocol, is the primary method used by the internet to transfer information between a browser and a web server. The acronym HTTP appears at the beginning of a website's URL.

Websites with a valid SSL certificate use HTTPS instead, where the "S" stands for Secure. You can tell from the address bar whether a website uses a secure protocol.

<comp.DocsImage path="assets/diagrams/CloudCannon-Documentation-URL-Structure-Diagram.png" alt="A diagram of a URL shows labels for protocol, subdomain, domain, top-level domain, subdirectory, slug, and path." title="The parts of a URL" type="ui-snippet" />

Most browsers warn visitors before they attempt to visit an insecure website (i.e., HTTP instead of HTTPS). Depending on your browser, this can take the form of a white warning page where the user must explicitly choose to continue to the insecure website.

Warnings about insecure websites can lead to a higher user bounce rate (where users immediately "bounce" off your website before seeing any of your content). This might be because users are security conscious or because they lose interest due to an inefficient experience.

You can avoid these issues by adding an SSL certificate to your *Site* to enable HTTPS.

## How do SSL certificates work?

SSL certificates contain the following details about your *Site*:

* **Domain name** — The address used to access a website (e.g., <a href="https://cloudcannon.com/">cloudcannon.com</a>).
* **Certificate expiration date** — The date a certificate expires. Auto-generated SSL certificates on CloudCannon renew automatically before they expire.
* **Public key** — A string used to encrypt data, protecting communication channels from unauthorized access. Data can only be decrypted with the corresponding private key.
* **Certificate chain** — A sequence of certificates that links the SSL certificate for your *Site* to a trusted certificate authority, providing legitimacy to your SSL certificate.
* **Private key** — A string used to decrypt data. The private key comes with the certificate, but is not shared with the visitor's browser.

<comp.Notice info_type="important">
  Give your private key only to the service that serves your website, such as CloudCannon. Do not write down your private key in a publicly accessible or insecure place. If you think the security of your private key has been compromised, please generate a new SSL certificate.
</comp.Notice>

When a browser attempts to connect to your website, it uses a process called a TLS handshake. This process validates the identity of the web server, the domain of your website, and prevents unauthorized access to the data passing between the user and your website.

In simple terms, the TLS handshake includes the following steps:

1. The user's browser contacts the web server hosting your website, listing the TLS versions and encryption methods the browser supports.
2. The web server replies with the TLS version and encryption method to use, and its SSL certificate.
3. The browser checks that the SSL certificate covers the domain, hasn't expired, and has a certificate chain that leads to a certificate authority the browser already trusts.
4. The web server proves it holds the private key that matches the public key in the SSL certificate, and the browser and the web server agree on a session key that only they know.
5. The browser and the web server use the session key to encrypt everything they send each other for the rest of the session.

This process only takes milliseconds to complete, so it does not affect the user's experience on your website.

Depending on your browser, a padlock icon appears near your URL once you add an SSL certificate to your website. You can click on this icon to review the publicly available certificate information.

## TLS version

Each <comp.GlossaryTerm term="/user/glossary/c/custom-domain.yml">Custom Domain</comp.GlossaryTerm> you host on CloudCannon has a minimum TLS version.

* **Minimum TLS version** — The minimum version of TLS that a visitor's internet browser must have to access your *Site*.

A higher TLS version is a stronger cryptographic standard, including fixes for known vulnerabilities in previous versions. On CloudCannon, the minimum TLS version you can use for your *Site* is 1.2, however 1.3 is available if you require it.

Raising the minimum TLS version improves security, but visitors using older internet browsers or devices that do not support that version can no longer reach your *Site*. TLS 1.2 is widely supported across current browsers, so raise the minimum to 1.3 only when you are confident your visitors' clients support it.

You set the minimum TLS version once for each *Custom Domain*, and CloudCannon shows which of its *Subdomains* meet it. You can also raise it for a single *Subdomain*. For more information, please read our documentation on [increasing the minimum TLS version for your domains](/documentation/developer-articles/increase-the-minimum-tls-version-for-your-domains/).

## Which SSL certificate is right for your domain?

On CloudCannon, each <comp.GlossaryTerm term="/user/glossary/s/subdomain.yml">Subdomain</comp.GlossaryTerm> of a *Custom Domain* has its own certificate, which covers every *Site* on that *Subdomain*. A *Subdomain* can use an [auto-generated SSL certificate](/documentation/developer-articles/add-an-auto-generated-ssl-certificate/) or a [custom SSL certificate](/documentation/developer-articles/add-a-custom-ssl-certificate/).

The domain's <comp.GlossaryTerm term="/user/glossary/w/wildcard-certificate.yml">wildcard certificate</comp.GlossaryTerm> covers subdomains you haven't set up yet (e.g., \*.example.com), so visitors to those subdomains reach your <comp.GlossaryTerm term="/user/glossary/f/fallback-redirect.yml">fallback redirect</comp.GlossaryTerm> over HTTPS. Every <comp.GlossaryTerm term="/user/glossary/b/base-domain.yml">Base Domain</comp.GlossaryTerm> (e.g., example.com) gets a wildcard certificate when you connect it, whatever its hosting.

### Auto-generated SSL certificates

CloudCannon provides a free auto-generated SSL certificate by default for each *Subdomain* you host on CloudCannon, and renews it automatically.

An auto-generated SSL certificate may be right for you if you want CloudCannon to manage your certificates for you.

If you use an auto-generated SSL certificate with <comp.GlossaryTerm term="/user/glossary/e/external-dns.yml">external DNS</comp.GlossaryTerm>, you need to add new TXT records at each renewal of the wildcard certificate for your *Base Domain*, or add one CNAME record that lets Cloudflare renew it on its own. For more information, please read our documentation on [renewing the wildcard certificate on external DNS](/documentation/developer-articles/add-an-auto-generated-ssl-certificate/#renew-the-wildcard-certificate-on-external-dns).

For more information, please read our documentation on [adding an auto-generated SSL certificate](/documentation/developer-articles/add-an-auto-generated-ssl-certificate/).

### SSL certificates on external DNS

If your *Custom Domain* uses external DNS, how an address gets HTTPS depends on whether you have added it as a *Subdomain* on CloudCannon:

* **Subdomains you have added** — Each *Subdomain*, including each <comp.GlossaryTerm term="/user/glossary/r/redirect-subdomain.yml">Redirect Subdomain</comp.GlossaryTerm>, gets its own certificate. Once the *Subdomain's* DNS record points at CloudCannon, CloudCannon validates the certificate over HTTP, so you usually don't need to add TXT records. If a *Subdomain* does need one, its *HTTPS* section lists it.
* **Subdomains you haven't added** — Only the wildcard certificate for your *Base Domain* covers these subdomains. Visitors only reach them if you add a wildcard DNS record (e.g., \*.example.com). The TXT records for the first wildcard certificate are optional, because your *Base Domain* and the *Subdomains* you have added have their own certificates. Once you have a wildcard certificate, it needs new TXT records at your DNS provider each time it renews, unless you add the one CNAME record that lets Cloudflare renew it on its own. Until the wildcard certificate is active, visitors to these subdomains see a security warning.

If visitors use an address on your domain, such as www.example.com, add it as its own *Subdomain* rather than relying on the fallback redirect and the wildcard certificate. To send its visitors somewhere else, add it as a *Redirect Subdomain*. *Redirect Subdomains* do not count toward the number of *Custom Domains* in your <comp.GlossaryTerm term="/user/glossary/s/subscription-plan.yml">Subscription Plan</comp.GlossaryTerm>. When you add your *Base Domain* as a new *Subdomain* to serve a *Site*, CloudCannon adds www.example.com as a redirect to it for you, unless www.example.com already exists, and the reverse when you add www.example.com. For more information, please read our documentation on [managing your Redirect Subdomains](/documentation/developer-articles/manage-your-redirect-subdomains/).

If you manage your DNS in your own Cloudflare account and set a record's proxy status to *Proxied*, set the *Subdomain's* hosting to <comp.GlossaryTerm term="/user/glossary/c/cloudflare-proxy.yml">Cloudflare Proxy</comp.GlossaryTerm>. For more information, please read our documentation on [configuring Cloudflare Proxy](/documentation/developer-articles/configure-external-dns/#configure-cloudflare-proxy).

### Custom SSL certificates

You can purchase a custom SSL certificate from a trusted third-party service and add your certificate details to CloudCannon. Each certificate you upload is saved to your <comp.GlossaryTerm term="/user/glossary/o/organization.yml">Organization</comp.GlossaryTerm>. The *SSL Certificates* page under *Org Settings* shows when each certificate expires and which *Subdomains* use it.

CloudCannon can't renew a certificate you upload. CloudCannon emails everyone who can edit the settings of a *Base Domain* with a *Subdomain* that still uses the certificate 14 days and 3 days before it expires. When the certificate expires, CloudCannon switches each *Subdomain* still using it to a certificate CloudCannon issues and renews. For more information, please read our documentation on [what happens when an uploaded certificate expires](/documentation/developer-articles/add-a-custom-ssl-certificate/#when-an-uploaded-certificate-expires).

* **Custom SSL certificate** — A certificate you have generated using a trusted third-party service (e.g., GoDaddy, Google, AWS, Cloudflare). Most web hosting services also provide the option to generate custom SSL certificates.

A custom SSL certificate may be right for you if:

* You already have an SSL certificate purchased through a third-party provider.
* Your company's security policies require you to have an SSL certificate from an internally approved authority.

For more information, please read our documentation on [adding a custom SSL certificate](/documentation/developer-articles/add-a-custom-ssl-certificate/).
