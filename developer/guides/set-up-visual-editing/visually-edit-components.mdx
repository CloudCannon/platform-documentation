<comp.Notice info_type="info">
  <p><comp.GlossaryTerm term="/user/glossary/c/component-editable-region.yml">Component Editable Regions</comp.GlossaryTerm> are available for Astro, Eleventy, and Hugo, and for sites built with React, Vue, or Svelte, including Next.js, Nuxt, and SvelteKit. The code examples in this step of the guide use Astro.</p><p><em>Component Editable Regions</em> are not yet available for other SSGs. Please get in touch with our friendly <a href="https://cloudcannon.com/support/">support team</a> to make a request.</p>
</comp.Notice>

Many static websites use reusable code components (a.k.a., partials) ranging from a small snippet of HTML, to UI elements like a header, profile card, or an entire page layout.

You can use the *Component Editable Regions* to re-render changes to your components in the Visual Editor, or enable inline editing of component text and images in conjunction with other *Editable Regions*. Let's cover how to define one.

<comp.Notice info_type="info">
  <p><strong>Nested text or image values</strong></p><p>To avoid <code>data-prop</code> misconfiguration errors, it is best practice to define your <em>Editable Regions</em> from the root of your file first (i.e., from parent elements to child elements). If you want to edit text or image values in a component using the Visual Editor, you should define your <em>Component Editable Region</em> on the parent element before Text and Image.</p>
</comp.Notice>

## Install the integration for your SSG

Unlike other types of *Editable Region*, *Component Editable Regions* need an integration, because CloudCannon re-renders your components in the browser rather than on a build server. Astro and Eleventy install an NPM package, Hugo installs a Hugo module, and sites built with React, Vue, or Svelte add a root component to your layout. You only need to do this once per *Site*.

<comp.Tabs label="Static site generators">
  <comp.Tab name="Astro">
    ### Astro

    Install the NPM package, then add the *Editable Regions* integration to your Astro configuration file.

    <comp.CodeBlock language="">
    ``````````

    npm install @cloudcannon/editable-regions

    ``````````
    </comp.CodeBlock>

    <comp.CodeBlock language="JavaScript" source="astro.config.mjs">
    ``````````

    import editableRegions from "@cloudcannon/editable-regions/astro-integration";
    import { defineConfig } from "astro/config";

    export default defineConfig({
      integrations: [editableRegions()],
    });

    ``````````
    </comp.CodeBlock>
  </comp.Tab>
  <comp.Tab name="Eleventy">
    ### Eleventy

    Install the NPM package, then add the *Editable Regions* plugin to your Eleventy configuration file.

    <comp.CodeBlock language="">
    ``````````

    npm install @cloudcannon/editable-regions

    ``````````
    </comp.CodeBlock>

    <comp.CodeBlock language="JavaScript" source="eleventy.config.mjs">
    ``````````

    import editableRegions from "@cloudcannon/editable-regions/eleventy";

    export default function (eleventyConfig) {
      eleventyConfig.addPlugin(editableRegions);

      return {
        dir: { input: "src", includes: "_includes", output: "_site" },
      };
    }

    ``````````
    </comp.CodeBlock>

    After every build, the plugin writes a `register-components.js` file into your output directory. Import it from your layout, inside the `<body>` element.

    <comp.CodeBlock language="HTML" source="base.liquid">
    ``````````

    <script>
      if (window.inEditorMode) {
        import("/register-components.js").catch((error) => {
          console.warn("Failed to load CloudCannon component registration:", error);
        });
      }
    </script>

    ``````````
    </comp.CodeBlock>
  </comp.Tab>
  <comp.Tab name="Hugo">
    ### Hugo

    Hugo uses a Hugo module rather than an NPM package. Install the module, add it to your Hugo configuration file, then include the *Editable Regions* partial in the `<head>` element of your base layout.

    <comp.CodeBlock language="">
    ``````````

    hugo mod get github.com/CloudCannon/editable-regions

    ``````````
    </comp.CodeBlock>

    <comp.CodeBlock language="TOML" source="hugo.toml">
    ``````````

    [module]
      [[module.imports]]
        path = "github.com/CloudCannon/editable-regions"
        version = "<version>"

    ``````````
    </comp.CodeBlock>

    <comp.CodeBlock language="HTML" source="layouts/_default/baseof.html">
    ``````````

    {{ partial "editable-regions" . }}

    ``````````
    </comp.CodeBlock>
  </comp.Tab>
  <comp.Tab name="JavaScript">
    ### JavaScript frameworks

    Install the NPM package, then wrap your routed page content in the `EditableRegions` component, in your root layout.

    <comp.CodeBlock language="">
    ``````````

    npm install @cloudcannon/editable-regions

    ``````````
    </comp.CodeBlock>

    <comp.CodeBlock language="JSX" source="app/layout.js">
    ``````````

    import { EditableRegions } from "@cloudcannon/editable-regions/react";

    export default function RootLayout({ children }) {
      return (
        <html lang="en">
          <body>
            <EditableRegions tag="main">{children}</EditableRegions>
          </body>
        </html>
      );
    }

    ``````````
    </comp.CodeBlock>

    Import `EditableRegions` from `@cloudcannon/editable-regions/react`, `/vue`, or `/svelte`, depending on your framework.
  </comp.Tab>
</comp.Tabs>

Your SSG may need more than this to build in the Visual Editor. For Astro framework renderers, Eleventy's `includeWith` tag, Hugo module vendoring, and static export settings for Next.js, Nuxt, and SvelteKit, please read our documentation on [configuring Component Editable Regions](/documentation/developer-articles/configure-component-editable-regions/). You can also visit CloudCannon's GitHub repository for the <a href="https://github.com/CloudCannon/editable-regions" target="_blank" rel="noopener noreferrer">Editable Regions NPM package</a>.

## Register your components

Registering a component tells CloudCannon which component a `data-component` value refers to, and that it should be bundled for client side use in the Visual Editor. Astro and the JavaScript frameworks need you to register each component by name. Eleventy and Hugo work out the name from your include and partial names, so they have no registration step.

<comp.Tabs label="Static site generators">
  <comp.Tab name="Astro">
    ### Astro

    Create a registration file for your components, then import it from your layout, inside the `<body>` element.

    If you use `.astro` component files, even if you have React components nested in them, import `{ registerAstroComponent }` in your registration script. Here's an example for the CTA component.

    <comp.CodeBlock language="JavaScript" source="src/scripts/register-components.js">
    ``````````

    import { registerAstroComponent } from '@cloudcannon/editable-regions/astro';
    import '@cloudcannon/editable-regions/astro-react-renderer'; /*1*/
    import CTA from '../components/CTA.astro';

    // Register your components
    registerAstroComponent('cta', CTA);

    ``````````
    <comp.Annotation number="1">
      This import is only necessary if you use React components nested inside your Astro components.
    </comp.Annotation>
    </comp.CodeBlock>

    If you use `.tsx` or `.jsx` component files, import `{ registerReactComponent }` instead.

    <comp.CodeBlock language="JavaScript" source="src/scripts/register-components.js">
    ``````````

    import { registerReactComponent } from '@cloudcannon/editable-regions/react';
    import MyComponent from './MyComponent.jsx';

    registerReactComponent('my_component', MyComponent);

    ``````````
    </comp.CodeBlock>
  </comp.Tab>
  <comp.Tab name="Eleventy">
    ### Eleventy

    There is no registration step. CloudCannon resolves component names the same way your templates resolve includes, so `{% include "cta" %}` matches `data-component="cta"`.

    The plugin you added in the previous step copies your includes into the registration script it writes after every build.
  </comp.Tab>
  <comp.Tab name="Hugo">
    ### Hugo

    There is no registration step. CloudCannon resolves component names as partial names, so `data-component="cta"` and `data-component="cta.html"` both render `layouts/partials/cta.html`.
  </comp.Tab>
  <comp.Tab name="JavaScript">
    ### JavaScript frameworks

    Register your components from a file that only runs in the browser, such as a client component in Next.js or a client plugin in Nuxt.

    <comp.CodeBlock language="TypeScript" source="app/plugins/cloudcannon.client.ts">
    ``````````

    import { registerVueComponent } from "@cloudcannon/editable-regions/vue";
    import CTA from "../components/CTA.vue";

    export default defineNuxtPlugin(() => {
      if (window.inEditorMode) {
        registerVueComponent('cta', CTA);
      }
    });

    ``````````
    </comp.CodeBlock>

    Import `registerReactComponent` from `@cloudcannon/editable-regions/react` or `registerSvelteComponent` from `@cloudcannon/editable-regions/svelte` for those frameworks.
  </comp.Tab>
</comp.Tabs>

## Components in layout files

Components use templating to reference structured data keys. Layout files then reference a component file. At build time, CloudCannon populates the component with the correct values and outputs it to the layout's HTML webpage.

Let's take a look at an example.

This file is a blog post, containing the `cta` object to the front matter, and the structured data keys `description`, `link`, `buttonText`, and `buttonColor`.

<comp.CodeBlock language="Markdown" source="first-post.mdx">
``````````

---
title: 'First post'
author: 'C. Kent'
heroImage: '../../assets/blog-banner.jpg'
heroImageTitle: 'Blog gradient'
heroImageAlt: 'An eye-catching color gradient banner.'
cta:
  description: "Need a little more help? Send a message to our friendly support team."
  link: "https://cloudcannon.com/support/"
  buttonText: "Send a message"
  buttonColor: "#034AD8"
---

Lorem ipsum dolor sit amet, consectetur adipiscing elit, sed do eiusmod tempor incididunt ut labore et dolore magna aliqua. Vitae ultricies leo integer malesuada nunc vel risus commodo viverra.

``````````
</comp.CodeBlock>

Here is an excerpt from our blog layout file, containing a Call-To-Action component called `CTA` at the bottom of every blog post.

<comp.CodeBlock language="Astro" source="BlogPost.astro">
``````````

---
import CTA from '../components/CTA.astro';
---

<html lang="en">
	<body>
		<main>
			<article>
                <!-- Blog HTML here -->
			</article>
			<CTA {...Astro.props.cta} /> /*1*/
		</main>
	</body>
</html>

``````````
<comp.Annotation number="1">
  The `<CTA>` component uses structured data in the front matter of the files in the Blog collection.
</comp.Annotation>
</comp.CodeBlock>

Finally, here's our component layout file, which contains HTML for the component and templating to populate elements with values from each blog file.

<comp.CodeBlock language="Astro" source="components/CTA.astro">
``````````

---
const { description, link, buttonText, buttonColor } = Astro.props;
---

<p>{description}</p>
<a href={link}>
    <button style={`background-color: ${buttonColor}`}>{buttonText}</button>
</a>

``````````
</comp.CodeBlock>

Together, these files output a webpage that looks like this:

<comp.DocsImage path="/assets/external_screenshots/CloudCannon-Documentation-Visual-Editing-Guide-CTA-Component.png" alt="A screenshot of a blog page on our Astro website shows a call to action component under the blog content." title="A blog page" type="screenshot"/>

In this example, the `<CTA>` component uses the properties in the `cta` object in each blog post. We can add a *Component Editable Regions* to our layout file to enable the Visual Editor to re-render any changes made with the data panel or sidebar.

First you need to import the component registration file you made earlier with a `<script>` HTML element. The `<script>` element should go inside the `<body>` element of your layout, which could be a different file depending on how your *Site* is structured (e.g., you may have a base layout file that all your other layouts reference). When you import the component registration file, you can also add instructions to check if your browser window is in Editor Mode (i.e., your webpage is open in CloudCannon's Visual Editor) and add an error warning.

Next, since the `<CTA>` component lacks an appropriate parent DOM element, you should wrap it in the `<editable-component>` web component. Our *Component Editable Region* also needs a `data-prop` to define where our component data is stored which, in this case, will be the `cta` front matter object in our blog post.

Finally, you need to add the `data-component` HTML attribute to define which registered component we are using which, in this case, is also called `cta`.

Here's what our Blog Layout code should look like:

<comp.CodeBlock language="Astro" source="BlogPost.astro">
``````````

<html lang="en">
  <body>
    <script> /*1*/
      if (window.inEditorMode) {
        import("../scripts/register-components.js").catch((error) => {
          console.warn("Failed to load CloudCannon component registration:", error);
        });
      }
    </script>
    <main>
      <article>
        <!-- Blog HTML here -->
      </article>
      <editable-component data-prop="cta" data-component="cta"> /*2*/
        <CTA {...Astro.props.cta} />
      </editable-component>
    </main>
    <Footer />
  </body>
</html>

``````````
<comp.Annotation number="1">
  The `<script>` element instructs your browser to import the `register-components.js` file if your webpage is open in the Visual Editor.
</comp.Annotation>
<comp.Annotation number="2">
  The `editable-component` web component defines a *Component Editable Region*. The `data-prop` attribute defines the path to the data we want to edit, and the `data-component` defines which registered component we are using. In this case, we want to edit the `cta` structured data key in the blog front matter and use the registered component `cta`.
</comp.Annotation>
</comp.CodeBlock>

If we were to save and rebuild our *Site* now, the Visual Editor would allow you to re-render the CTA component when you edit values using the data panel or sidebar, but would not allow inline editing for the text values `description` and `buttonText`. To achieve this, we also need to add <comp.GlossaryTerm term="/user/glossary/t/text-editable-region.yml">Text Editable Regions</comp.GlossaryTerm> to the CTA component file.

Here's what our CTA component code should look like:

<comp.CodeBlock language="Astro" source="components/CTA.astro">
``````````

---
const { description, link, buttonText, buttonColor } = Astro.props;
---

<p data-editable="text" data-prop="description">{description}</p>
<a href={link}>
    <button data-editable="text" data-prop="buttonText" style={`background-color: ${buttonColor}`}>{buttonText}</button>
</a>

``````````
<comp.Annotation number="1">
  This `<p>` element contains `data-editable="text"` and `data-prop="description"` to define a *Text Editable Region*.
</comp.Annotation>
<comp.Annotation number="2">
  This `<button>` element contains `data-editable="text"` and `data-prop="buttonText"` to define a *Text Editable Region*.
</comp.Annotation>
</comp.CodeBlock>

Once we save and rebuild our *Site*, CloudCannon will show a yellow *Editable Regions* box around all the content inside the `<CTA>` component in the Visual Editor. There are also two *Text Editable Regions* around the description and button text.

<comp.DocShot docshot_key="CloudCannon-Documentation-Visual-Editor-Component-Editable-Region" alt="A screenshot of the Visual Editor shows a yellow Editable Region box around the Call to Action component on the blog page." title="Component Editable Region in the Visual Editor" type="screenshot"/>

When you click into the *Editable Region*, CloudCannon will open a data panel with inputs for all four structured data keys in the component: `description`, `link`, `buttonText`, and `buttonColor`.

## Common errors

If you accidentally misconfigure your *Editable Regions*, CloudCannon will replace them in the Visual Editor with a red *Error Card* naming the region type and describing the problem.

<comp.DocShot docshot_key="CloudCannon-Documentation-Visual-Editor-Component-Editable-Region-Error-Element" alt="A screenshot of an Error Card in the Visual Editor shows a message headed Failed to render component, followed by the reason the region could not render." title="A misconfigured Component Editable Region in the Visual Editor" type="ui-snippet"/>

Here are a few common errors you might encounter with *Component Editable Regions*:

* You did not define the `data-prop` or `data-component`HTML attributes.
* The *Editable Region* has an invalid data type (e.g., your Text region has a number or object, instead of a string).
* You reference a component that does not exist, or has not been registered.
* Component rendering errors
* Invalid component return values
